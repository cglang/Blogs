JavaScript 是单线程语言，却能同时处理定时器、网络请求和用户交互，靠的就是**事件循环（Event Loop）**。理解它，才能解释 `setTimeout` 为什么不准确、`Promise` 为什么比定时器先执行。

## 核心概念

- **调用栈（Call Stack）**：当前正在执行的同步代码。
- **宏任务（Macro Task）**：`setTimeout`、`setInterval`、I/O、UI 事件。
- **微任务（Micro Task）**：`Promise.then`、`queueMicrotask`、`MutationObserver`。
- **渲染时机**：每轮宏任务结束后，浏览器有机会进行样式计算、布局与绘制。

## 执行流程

```text
执行同步代码
  └─> 清空所有微任务
        └─> 浏览器渲染
              └─> 取出下一个宏任务
```

> 关键规则：**每执行完一个宏任务，就会清空当前所有微任务，然后才进入下一次渲染或下一个宏任务。**

## 一道经典面试题

```js
console.log("script start");

setTimeout(() => {
  console.log("setTimeout");
}, 0);

Promise.resolve()
  .then(() => console.log("promise 1"))
  .then(() => console.log("promise 2"));

console.log("script end");
```

输出顺序：

```text
script start
script end
promise 1
promise 2
setTimeout
```

原因：同步代码先执行，随后清空微任务队列，最后才轮到 `setTimeout` 所在的宏任务。

## 用 async/await 再验证一次

```js
async function main() {
  console.log("main start");
  await Promise.resolve();
  console.log("after await");
}

main();
console.log("sync end");
```

`await` 之后的代码等价于放进 `then` 回调，因此输出为：

```text
main start
sync end
after await
```

## 常见误区

| 误区 | 事实 |
| --- | --- |
| `setTimeout(fn, 0)` 会立即执行 | 至少等到下一个宏任务，通常 ≥ 4ms |
| 微任务可以无限嵌套 | 会导致页面一直无法渲染，需警惕死循环 |
| `requestAnimationFrame` 是宏任务 | 它属于渲染前回调，时机早于下一轮宏任务 |

## 小结

1. 同步代码 → 微任务 → 渲染 → 下一个宏任务。
2. `Promise` 回调优先级高于 `setTimeout`。
3. 大量同步微任务会阻塞渲染，重活应交给 `setTimeout` 或 `requestIdleCallback` 分片。

理解事件循环后，排查「为什么页面卡顿」「为什么状态更新有延迟」会轻松很多。
